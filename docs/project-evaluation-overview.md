# EvalForge 项目汇报梳理

> 用途：项目目标、架构、评测集质量指标、前端字段口径、当前进展与后续规划。
>
> 口径说明：文档中的“当前实现”以当前代码和模块 README 为准；“建议口径”用于后续产品化和汇报统一，不代表已经全部落地。

## 1. 项目定位与目标

EvalForge 是一个评测集生产、质量治理、版本管理和 Agent 评测平台，不是单纯的 RAG 问答系统。

平台的目标是把业务文档中的知识转换为可审计、可复现、可评测的问答样本，并使用同一份冻结评测集比较不同智能体版本的能力。

核心目标：

1. 将非结构化业务文档解析为结构化知识单元 EIU。
2. 基于 EIU 生成带标准答案和原文证据的问答对。
3. 通过质量检查和覆盖率门禁，保证评测集可用、可信、可追溯。
4. 使用冻结后的评测集运行目标智能体，并输出准确性、稳定性、耗时、成本和失败记录。

核心原则：

- 原文是事实的唯一来源。
- EIU 是文档与评测集之间的核心中间层。
- 评测集冻结后不可直接修改，保证不同智能体之间公平比较。
- 平台负责评测与诊断，不负责自动修改目标智能体。

## 2. 总体架构

```text
文档上传
  ↓
文档解析 → Block 结构化分段与原文定位
  ↓
EIU 抽取、分类、去重、向量化
  ↓
覆盖规划
  ↓
问题、标准答案、证据绑定生成
  ↓
问答质量检查
  ↓
评测集版本冻结
  ↓
多来源评测集组合
  ↓
目标智能体批量评测
  ↓
指标汇总、失败记录、版本对比
```

架构分为四层：

| 层次 | 主要职责 |
|---|---|
| 接入层 | 前端管理台、FastAPI HTTP API |
| 业务层 | 文档解析、EIU 抽取、问答生成、质量治理、版本管理、Agent 评测 |
| 数据层 | MySQL、原始文件存储、FAISS EIU 向量索引 |
| 模型层 | BGE Embedding、LLM 抽取/生成/质检 |

### 2.1 核心模块

| 模块 | 职责 | 当前状态 |
|---|---|---|
| M01 数据基础 | 文档上传、解析、Block、原文定位、EIU 向量化 | 已实现 |
| M02 EIU 抽取与覆盖 | EIU 抽取、分类、去重、覆盖统计 | 已实现 |
| M03 评测集生成 | 问题、答案、证据、难度和泛化生成 | 已实现单段主链路 |
| M04 质量治理 | 五项基础质量检查、复检和状态管理 | 已实现基础能力 |
| M05 数据集生命周期 | 编辑、冻结、来源组合、导出和版本管理 | 已实现基础能力 |
| M07 智能问答 | 对话式平台操作 | Demo 暂不重点建设 |
| M08 Agent 评测 | 适配器、批量运行、评分、诊断、ErrorBook | 已实现黑盒评测 |

### 2.2 核心数据对象

```text
document
  └── block
        └── eiu
              └── eval_case（问题、答案、证据）
                    ├── quality_check_result
                    ├── dataset_version
                    └── evaluation_case_result
```

评测集还支持三类来源：

- 文档生成评测集；
- 用户上传评测集；
- 公共评测集库。

## 3. 什么是“好”的评测集

好的评测集不只是题目数量多，而应同时满足：

```text
覆盖完整
+ 内容正确
+ 问答可判定
+ 证据可追溯
+ 难度有区分度
+ 表述具有泛化性
+ 题目低冗余
+ 能公平比较智能体
+ 失败后能够定位问题
+ 能够稳定复测
```

质量链路应按以下四层检查：

```text
文档 → EIU → 问答对 → 评测集
```

## 4. 核心质量指标

### 4.1 文档 → EIU

这一层回答：文档中的有效业务事实，是否被完整、准确、可追溯地抽取为 EIU？

| 指标 | 定义 | 作用 |
|---|---|---|
| 实质 Block 对账率 | 有 EIU 或明确排除原因的实质 Block / 实质 Block 总数 | 防止文档内容无声丢失 |
| EIU 抽取覆盖率 | 被有效 EIU 覆盖的实质 Block / 实质 Block 总数 | 衡量抽取完整性 |
| EIU 抽取密度 | EIU 数 / 实质 Block 数 | 发现抽取过少或过度拆分 |
| EIU 证据绑定率 | 具备有效文档、章节、页码、原文片段定位的 EIU / EIU 总数 | 衡量可追溯性 |
| EIU 完整性通过率 | 具备陈述、类型、优先级和约束字段的 EIU / EIU 总数 | 衡量结构化质量 |
| 可出题率 | `is_questionable=true` 的 EIU / EIU 总数 | 判断知识是否能转为评测任务 |
| 合理排除率 | 排除原因符合规则的 EIU / 排除 EIU 总数 | 防止用“难出题”掩盖抽取缺失 |
| 重复 EIU 率 | 重复或高度相似 EIU / EIU 总数 | 防止分母膨胀和重复计权 |
| 人工抽样准确率 | 人工确认正确的 EIU / 抽样 EIU 总数 | 评估抽取 precision |
| EIU 漏检率 | 人工发现但系统未抽取的有效事实 / 人工标注有效事实总数 | 评估抽取 recall |

当前最重要的三个指标是：实质 Block 对账率、EIU 证据绑定率、人工抽样准确率/漏检率。

### 4.2 EIU 本身

这一层回答：每条 EIU 是否真的是独立、准确、可评测的信息单元？

| 指标 | 检查内容 |
|---|---|
| 独立性 | EIU 能否独立判断真假 |
| 原子性 | 是否错误合并多个独立事实 |
| 完整性 | 主体、条件、范围、期间、单位、例外是否完整 |
| 事实忠实性 | EIU 是否完全受到原文支持 |
| 证据充分性 | 原文证据是否覆盖 EIU 全部陈述 |
| 上下文自足性 | 脱离原段落后是否仍能正确理解 |
| 类型准确率 | definition、rule、threshold 等分类是否正确 |
| 优先级准确率 | P0/P1/P2 是否符合业务重要性 |
| 去重率 | 是否与其他 EIU 表达同一事实 |
| 冲突识别率 | 是否识别新旧版本、例外和冲突规则 |
| 可回答性 | 是否能形成明确问题和答案 |
| 排除合理性 | 不可出题 EIU 是否有真实、明确的排除原因 |

EIU 质量可以抽象为：

```text
EIU 质量 = 忠实性 × 完整性 × 独立性 × 可回答性 × 可追溯性
```

任一关键项失败，都不应直接进入正式评测集。

### 4.3 单个问答对

这一层回答：这道题是否真的能测试目标能力，并且答案可以客观判定？

当前已有五项基础检查：

1. 可回答性；
2. 答案忠实性；
3. 答案唯一性；
4. 证据充分性；
5. 问题相关性。

建议补充以下指标：

| 指标 | 定义 |
|---|---|
| 答案正确性 | 标准答案与原文事实一致 |
| 答案完整性 | 覆盖全部必须命中的答案要点 |
| 答案唯一性 | 未遗漏其他同样合理的答案 |
| 证据忠实性 | 答案未超出原文证据 |
| 问题非泄漏性 | 问题没有直接透露答案 |
| 题型匹配度 | 题型与 EIU 类型匹配 |
| 难度有效性 | L1/L2/L3 标注合理 |
| 答案判定性 | 可以用明确规则判断目标回答是否正确 |
| 表述泛化性 | 同义、口语、不同语序仍对应同一答案 |
| 重复率 | 与其他题不是重复考查同一能力 |
| 多跳真实性 | 跨段题确实需要多个证据共同推理 |

单题质量可以抽象为：

```text
单题质量 = 可回答性 × 正确性 × 完整性 × 忠实性 × 证据充分性 × 区分度
```

### 4.4 整个评测集

#### 覆盖指标

当前加权覆盖率为：

```text
Weighted Coverage = Σ(权重 × 是否被有效题目覆盖) / Σ权重
```

权重为：

```text
P0 = 5，P1 = 3，P2 = 1
```

建议展示：

- 总体加权覆盖率；
- P0/P1/P2 覆盖率；
- 按文档、章节、EIU 类型和题型的覆盖率；
- 未覆盖 EIU 清单；
- 不可出题 EIU 数量及原因。

当前发布门禁：

```text
总体加权覆盖率 ≥ 85%
P0 覆盖率 = 100%
实质 Block 对账率 = 100%
```

85% 是评测集发布覆盖门槛，不是评测集质量的全部定义。

#### 代表性指标

| 指标 | 作用 |
|---|---|
| 题型覆盖度 | 是否覆盖定义、规则、阈值、例外、流程等能力 |
| 难度分布 | 是否同时包含 L1、L2、L3 |
| 维度覆盖度 | 是否覆盖业务、合规、风控和专业能力 |
| 文档覆盖度 | 是否集中在少数文档 |
| 多跳占比 | 是否覆盖跨段、跨文档推理 |
| 对抗题占比 | 是否覆盖易混淆和边界场景 |
| 不可回答题占比 | 是否检验正确拒答能力 |
| 计算题占比 | 是否覆盖公式和数值推理 |

#### 冗余和独立性指标

- 精确重复率；
- 语义重复率；
- EIU 重复计分率；
- 答案重复率；
- 同义变体有效率。

## 5. 前端字段定义

### 5.1 问答对详情字段

| 前端字段 | 后端字段 | 定义 |
|---|---|---|
| 问题 | `question` | 发给目标智能体的测试输入，不应泄露答案 |
| 标准答案 | `gold_answer` | 基于原文证据编制的参考答案 |
| 必须命中要点 | `must_have_points` | 判断答案完整性的关键事实清单 |
| 可接受答案 | `acceptable_answers` | 与标准答案语义等价的表达 |
| 证据 | `evidence` | 支持问题和答案的原文证据及定位 |
| 题型 | `question_type` | definition、rule、threshold、formula、process 等 |
| 难度 | `difficulty` | L1/L2/L3，前端显示为简单/中等/难 |
| 范围 | `scope_type` | 单段、跨段、跨文档 |
| 内容优先级 | `content_priority` | P0/P1/P2，表示业务重要性 |
| 评审状态 | `review_status` | candidate、needs_review、quality_verified 等 |
| 来源 | `source` | 文档生成、上传库、公共库 |

### 5.2 难度字段

| 难度 | 前端显示 | 判定标准 |
|---|---|---|
| L1 | 简单 | 单段直接事实，不需要复杂推理 |
| L2 | 中等 | 条件判断、轻度消歧、相邻段落关联或简单计算 |
| L3 | 难 | 跨段/跨文档、多跳、计算、版本比较或对抗场景 |

难度表示解题复杂度，不表示业务重要性。业务重要性由 P0/P1/P2 表示。

建议保留难度判定依据，例如证据数量、跳数、是否跨文档、是否计算和是否需要消歧。

### 5.3 单题评测结果字段

| 字段 | 定义 |
|---|---|
| 状态 | 通过、未通过、错误、未评分 |
| 评分 | 目标回答与标准答案的匹配分数，前端显示为 0–100 |
| 问题 | 本次发送的问题 |
| 金标准 | 评测集中的标准答案 |
| 目标回答 | 目标智能体返回的最终答案 |
| 维度 | 所属业务能力或评测维度 |
| 难度 | 题目复杂度 |
| 诊断 | 当前主要为 E2E 或 D9 |
| 复测记录 | 同一题后续尝试，不覆盖原始结果 |

当前评分口径：

- 短答案使用规范化精确匹配；
- 长答案尝试使用 BGE 语义相似度；
- 语义模型不可用时回退到精确匹配；
- 当前 `score >= 0.5` 判定为通过。

建议前端同时展示评分方式和判定阈值，例如“评分 82，语义相似度，阈值 50”。

## 6. 评测运行概览指标

### 6.1 当前指标口径

| 前端指标 | 定义 |
|---|---|
| 总题数 | 本次实际加载的评测样本数 |
| 已评分 | 具有有效 `score` 的样本数 |
| 通过数 | `score >= 0.5` 的样本数 |
| 通过率 | 当前为 `通过数 / 已评分数` |
| 错误数 | `status == error` 的样本数 |
| 错误率 | `错误数 / 总题数` |
| 诊断分布 | E2E、D9 等诊断码的数量分布 |
| 按难度 | 各难度的总题数、通过数和通过率 |
| 按维度 | 各业务维度的总题数、通过数和通过率 |
| 总耗时 | 所有样本耗时之和 |
| 总 Token 数 | 所有样本 Token 消耗之和 |
| 总成本 | 所有样本成本之和 |

建议新增并同时展示：

```text
评分通过率 = 通过数 / 已评分数
总体成功率 = 通过数 / 总题数
错误率 = 错误数 / 总题数
```

原因是评分通过率会排除调用错误。例如 100 道题中 90 道完成评分、72 道通过时：

```text
评分通过率 = 72 / 90 = 80%
总体成功率 = 72 / 100 = 72%
```

只展示 80% 会掩盖运行异常。

### 6.2 建议的运行概览卡片

评测运行页建议优先展示：

| 卡片 | 含义 |
|---|---|
| 总体成功率 | 通过数 / 总题数，体现整体交付效果 |
| 评分通过率 | 通过数 / 已评分数，体现答案质量 |
| 错误率 | 调用错误 / 总题数，体现运行稳定性 |
| 平均得分 | 已评分样本的平均 score |
| P95 耗时 | 95% 请求在该时长内完成 |
| 总成本 | 本次运行累计 Token 或费用 |

按难度和维度展开时，应同时显示：

```text
名称｜样本数｜通过数｜通过率｜错误率｜平均分
```

避免只展示一个百分比而忽略样本量。

## 7. 当前进展

当前已经具备：

- 文档上传、解析和原文定位；
- Block 层级结构；
- EIU 抽取、分类、向量化和覆盖率计算；
- 单段问题、答案和证据绑定生成；
- 五项基础质量检查；
- 评测集编辑、冻结、导出和版本管理；
- 文档生成、用户上传、公共库三类来源；
- 多来源评测集组合；
- Mock 和 OpenAI 兼容 Agent 适配器；
- 批量评测、结果汇总、耗时、Token 和成本统计；
- E2E/D9 失败记录、ErrorBook 和单题复测。

当前边界：

- EIU 抽取仍需要更完善的人工校准集；
- 质量治理目前主要是五项基础检查；
- 跨段和跨文档问题仍需增强；
- 目标智能体默认只返回最终答案，无法定位检索、事实、推理或计算环节错误；
- 语义评分阈值和固定校准集仍需业务确认；
- 外部 Agent 适配器仍需补充安全、并发、超时和成本治理。

## 8. 后续改进路线

### 8.1 问答对泛化

建立同一意图下的问答变体组：正式表达、口语表达、同义词替换、术语全称/简称、不同语序、场景先行和干扰信息。

建议使用 `intent_id` 管理变体：同一意图共享标准答案和 EIU 覆盖，不重复计覆盖率。

核心指标：

```text
泛化保持率 = 仍对应同一标准答案的变体数 / 变体总数
```

### 8.2 跨段和跨文档问题

真多跳题必须满足：

```text
证据 A 单独不足以回答
证据 B 单独不足以回答
只有组合 A+B 才能完整回答
```

候选发现可使用 EIU 向量近邻、共同主体、共同术语、规则/例外、指标/公式、新旧版本和引用关系。

建议指标：真多跳准确率、多跳证据召回率、单证据误标率、跨文档答案一致性和版本冲突识别率。

### 8.3 中间结果和错因定位

目标智能体未来可返回结构化结果：

```json
{
  "final_answer": "...",
  "retrieved_documents": [],
  "retrieved_blocks": [],
  "key_facts": {},
  "intermediate_steps": [],
  "calculations": {},
  "decision": "...",
  "confidence": 0.82
}
```

由此可以分层评估：

| 层级 | 指标 |
|---|---|
| 检索层 | Evidence Recall@K、MRR、nDCG@K |
| 事实层 | 关键事实召回率、事实准确率 |
| 推理层 | 中间节点正确率、步骤一致性 |
| 计算层 | 公式正确率、变量绑定正确率、数值误差 |
| 最终答案层 | EM、F1、语义相似度、要点召回率 |
| 引用层 | 引用准确率、引用完整率 |
| 拒答层 | 正确拒答率、幻觉率 |
| 运行层 | P50/P95 延迟、Token、成本、异常率 |

这样可以把“最终答案错误”进一步定位为检索失败、证据缺失、事实抽取错误、推理错误、计算错误或表达错误。

## 9. 汇报结论

项目的核心不是生成更多题目，而是建立一条从原文、EIU、问答对到评测报告的可追溯质量链路。

一个好的评测集必须在文档覆盖、EIU 正确性、单题可判定性和整体代表性四个层面同时达标，最终还要支持稳定复测和失败定位。

前端展示的每个指标都应明确：

1. 分子是什么；
2. 分母是什么；
3. 异常样本是否被排除；
4. 该指标是结构质量、语义质量、覆盖质量还是运行质量。

## 10. EIU 抽取与前端展示的落地口径（2026-08-26）

### 10.1 是否还需要切块

仍需要切块，但 Block 只承担文档结构恢复、原文定位、增量解析和证据引用，不再等同于 EIU 边界。系统采用三层对象：

1. **Evidence Block**：可定位的原文证据片段；
2. **Context Bundle**：当前 Block、上级结构、邻接上下文和显式引用条款组成的上下文包；
3. **Verified Claim（已验证知识声明）**：满足完整事实条件、可独立判定且证据充分的正式 EIU。

一个知识声明可以绑定多个 Block。若正文出现“按第十八条要求”“前款”“上述”等引用，系统将补充引用或上下文 Block，并把该项标记为跨块证据；启发式上下文无法完全消除歧义时，状态进入“待复核”。整篇文档不直接逐条送入 LLM，而是用结构和引用索引提供文档级导航，降低长上下文遗漏和解析成本。

### 10.2 候选与正式口径

规则和 LLM 的抽取结果首先都是**候选声明**，不得直接进入评测集。每条候选执行四项检查：

| 检查 | 定义 | 当前自动检查重点 |
|---|---|---|
| 忠实性 | 声明中的事实是否完全受原文支持 | 原文包含关系、数字一致性 |
| 完整性 | 主体、条件、范围、例外和引用是否足够 | 指代词、引用条款解析情况 |
| 原子性 | 是否只表达一个可独立判定的完整事实 | 长度、规范谓词数、复合分句 |
| 可测试性 | 是否能够形成稳定问题和标准答案 | 可判定谓词、量化条件、标题/附件误抽 |

| 状态 | 定义 | 进入正式覆盖率分母 | 允许生成问答对 |
|---|---|---:|---:|
| 候选 `candidate` | 已抽取，尚未形成质量结论 | 否 | 否 |
| 已验证 `verified` | 四项检查通过或经人工确认 | 是 | 是 |
| 待复核 `needs_review` | 存在跨块指代、复合事实或证据疑点 | 否 | 否 |
| 已排除 `rejected` | 无实质内容或明确不可出题，且有排除原因 | 否 | 否 |

正式覆盖率只以已验证且可出题的声明为分母；同时独立展示候选、待复核和排除数量，并继续执行实质 Block 对账，防止通过减少分母制造虚高覆盖率。

### 10.3 前端展示调整

- 概览计数：候选声明、已验证、待复核、已排除、跨块证据；
- 明细字段：知识声明、验证状态、四项质量检查通过数、优先级、类型、证据链、来源文档；
- 复杂度字段：按分句、规则谓词、量化条件和跨块依赖形成可解释的 L1/L2/L3 路由等级；该等级用于决定复核成本，不等同于问答对难度；
- 跨块声明显示“跨块”标签，并按“直接证据 → 引用条款/上下文”展示 Block 链；
- 平台概览把“知识点待复核”列为独立待办；
- 页面和项目汇报统一使用“知识点”：它表示从文档中抽取、绑定证据并接受质量检查的知识内容；接口、数据库和技术实现暂时保留 `EIU` 名称以保持兼容。

当前确定性检查是低成本第一道门禁。后续应以分层批处理方式对高风险候选增加 LLM 二次评审和人工抽样校准，而不是恢复全量逐条 LLM 抽取。

### 10.4 示例文档诊断

以 `data/documents/附件1：定期存单质押授信业务.docx` 做确定性规则阶段诊断：解析得到 60 个 Block，其中 28 个为非标题实质 Block；语义去重前得到 114 条候选声明。第一道质量门禁判定 57 条自动通过、57 条待复核；复杂度分布为 L1 102 条、L2 12 条；排除仅由上级标题造成的结构关联后，识别到 20 条真正依赖引用条款或邻接上下文的跨块候选。

该结果说明两个问题：一是不能用“候选数量”代表知识质量；二是固定前后窗口不足以处理条款引用，必须保留文档级引用索引和多 Block 证据链。示例中的文档标题曾因包含“2025”被误认为可测试内容，现已由标题规则拦截为待复核；这也说明确定性门禁只能承担低成本初筛，正式上线仍需人工校准集与高风险候选二次语义评审。
