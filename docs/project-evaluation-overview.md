# EvalForge 项目汇报与指标口径

> 用途：用于项目汇报、前端展示和验收沟通。
>
> **口径优先级**：本文以 2026-08-26 当前源码、API 返回和前端实际展示为准。为避免误导，明确标记“已实现”“仅有计算函数、未接入门禁”和“规划中”。

## 1. 项目目标

EvalForge 是一个把业务文档转化为可追溯评测集，并对目标智能体执行批量评测的平台。它不是 RAG 问答系统本身，而是用于检验 RAG / Agent 能力的评测基础设施。

平台要解决四个问题：

1. 文档内容是否被识别、定位和纳入知识点处理；
2. 知识点是否足以支撑一条有标准答案、有证据的问答对；
3. 问答对是否通过质量检查，能够冻结为可复现的评测集；
4. 目标智能体在同一份冻结评测集上的答题效果、调用稳定性和失败样本是什么。

核心原则：原文是事实来源；知识点和证据链是中间审计对象；冻结后的版本不可变；评测结果不覆盖原始记录。

## 2. 当前实际架构

```text
文档上传
  ↓
M01 解析为 Block（结构、页码、章节、原文定位）
  ↓
M02 规则抽取知识点候选 + 跨 Block 证据组装 + 四项质量检查
  ↓
M03 仅对“已验证、可出题”的知识点生成 QA 与证据绑定
  ↓
M04 LLM 五项问答质检；失败后复核或有限重生成
  ↓
M05 只将通过状态的生成题快照冻结，并可组合上传/公共来源
  ↓
M08 调用目标智能体、评分、汇总、记录 ErrorBook
```

| 层级 | 当前主要对象 | 作用 |
|---|---|---|
| 文档层 | `document`、`block` | 保留原文、结构和可定位证据；Block 不是知识点边界 |
| 知识层 | `eiu`（前端统一称“知识点”） | 保存候选陈述、类型、优先级、证据链和质量状态 |
| 样本层 | `generated_case`、`eval_case` | 保存问题、金标准、必答要点、可接受答案、证据和审核状态 |
| 运行层 | `evaluation_run`、`evaluation_case_result` | 保存目标回答、评分、耗时、成本、诊断和复测记录 |

## 3. 指标阅读指南：不要把四类数混成一个“质量分”

当前没有“评测集总质量分”。实际使用的是四类互补指标：

| 层次 | 回答的问题 | 当前主要指标 |
|---|---|---|
| 文档→知识点 | 文档内容有没有被纳入处理 | Block 对账率、候选/验证/待复核/排除数量、告警 |
| 知识点质量 | 该知识点是否足够忠实、完整、独立、可测试 | 四项规则检查、质量分、质量状态、复杂度 |
| QA 样本质量 | 题目、答案和证据能否构成可判定样本 | 五项质检通过/失败数及逐项通过率 |
| Agent 运行表现 | 目标智能体答得如何、运行是否稳定 | 通过率、错误率、难度/维度分组、耗时、Token、成本、诊断 |

因此，汇报时应分别说明“数据质量”和“被测智能体表现”。例如，Agent 通过率低不等于评测集质量差；它也可能揭示目标智能体能力不足。反之，QA 质检未通过的样本也不能用于证明 Agent 的能力高低。

## 4. 当前实际使用的质量检验与指标

### 4.1 文档 → 知识点：覆盖与对账（M02）

Block 仍然需要保留：它用于文档结构恢复、页码/章节定位、相邻上下文和证据链承载；系统不把“一个 Block”直接当作“一个知识点”。规则抽取的结果首先是候选，引用条款、父级 Block 与必要的前序上下文会补入证据链。

`GET /api/eiu/coverage` 的实际字段和定义如下。

| 字段 / 指标 | 实际定义 | 是否进入正式覆盖率 |
|---|---|---:|
| `total_eiu` | 未被软删除的全部知识点记录数，含可出题和不可出题项 | 否 |
| `candidate_eiu` | `is_questionable=true` 的候选知识点数 | 否 |
| `verified_eiu` | 候选中 `quality_status=verified`（兼容历史 `review_status=quality_verified`）的数量 | 是，作为分母 |
| `needs_review_eiu` | 候选中 `quality_status=needs_review` 的数量 | 否 |
| `rejected_eiu` / `excluded_eiu` | `is_questionable=false` 的记录数；应有 `exclusion_reason` | 否 |
| `by_priority` | 全部未删除知识点按 P0/P1/P2 的数量 | 仅结构分布 |
| `by_type` | 全部未删除知识点按类型的数量 | 仅结构分布 |
| `by_document` / `by_section` | 全部未删除知识点按文档/章节的数量 | 仅结构分布，不是覆盖率 |
| 加权覆盖率 `weighted_coverage` | 已被**可发布态**题目覆盖的已验证知识点权重之和 / 已验证知识点权重之和 | 是 |
| P0 覆盖率 `p0_coverage_pct` | 已覆盖 P0 已验证知识点数 / 全部 P0 已验证知识点数；没有 P0 时返回 100% | 是 |
| Block 对账率 `block_reconciliation.rate` | 至少关联一条知识点（包括不可出题排除记录）的非标题 Block 数 / 非标题 Block 总数 | 是，防遗漏 |

权重取值为 P0=5、P1=3、P2=1。所谓“已覆盖”不是只要生成过题：只有关联到该知识点且样本状态为 `quality_verified`、`governance_passed`、`user_confirmed` 或 `published` 时，才记入覆盖分子。

系统还会返回三类实际告警：排除项占全部记录超过 50%；排除原因含“难生成/难出题”；存在未对账 Block 或未验证候选。这些告警用于防止通过减少分母制造虚高覆盖率。

**重要边界**：代码中已经有“加权覆盖率≥85%、P0=100%、Block 对账率=100%”的 `assert_coverage_gate` 校验函数；但当前 M05 冻结流程按所选评测集快照可发布态题目，不会调用该全库门禁。因此这三个阈值目前只能作为健康目标/待接入门禁，不能在汇报中表述为“冻结时已强制拦截”。

### 4.2 知识点自身质量（M02）

每个候选知识点由 `EiuQualityEvaluator` 执行四项确定性检查。规则抽取后先走三色路由：绿色（直接、单一、证据完整）可继续确定性验证；黄色（多规则/引用/例外/列表/表格/长 Block/P0 或规则兜底分类）会携带同 Block 候选及相邻上下文批量送入 LLM 拆分、合并、补全和证据判断；LLM 不可用、调用失败或仍有疑点的红色项进入人工复核，不进入正式分母或自动出题。它仍不是人工标注意义上的抽取 Precision / Recall。

| 检查 | 当前规则 | 结果含义 |
|---|---|---|
| 忠实性 `fidelity` | 知识点陈述经规范化后应是证据文本子串；陈述中的数字应在证据中出现 | 防止改写、补写或数字漂移 |
| 完整性 `completeness` | 检测“上述、前款、相关要求”等指代；检查引用条款能否在文档中定位 | 发现脱离上下文后可能不完整的陈述 |
| 原子性 `atomicity` | 陈述超过160字、包含多个规范谓词、分号或多重冒号时告警 | 发现可能混合多项规则的陈述 |
| 可测试性 `testability` | 检测过短文本、标题/附件式文本、缺少规则谓词或量化条件 | 排除难以形成稳定问答的内容 |

每项检查当前只有 `pass`（1.0）和 `warning`（0.5）两类结果；`quality_score` 是四项得分的平均值。四项全通过才自动为 `verified`，任一告警为 `needs_review`；不可出题项为 `rejected`。人工修改陈述后会回退为待复核，避免沿用旧结论。

知识点还会计算 `complexity_score`（1–5）和 `complexity_level`：根据语义分句数、规则/条件谓词数、数值约束数、引用/上下文证据来判断。分数≤2 为 L1，3–4 为 L2，5 为 L3。**该复杂度用于判断知识点理解和复核成本，不等同于 QA 难度。**

跨 Block 信息的当前处理方式是：显式条款号匹配到引用 Block；父级 Block 加入证据；出现指代词时补充紧邻前一非标题 Block。它能发现一部分跨块依赖，但属于启发式，无法证明已经找全所有分散信息；存在指代会通过 `needs_review` 留给复核，而不会进入自动出题。

### 4.3 知识点 → QA：生成限制和单题质检（M03/M04）

M03 只对同时满足 `is_questionable=true` 且“已验证”的知识点生成问答。生成返回的 `quality_blocked` 表示候选中因未通过知识点质量验证而未进入出题的数量。

生成时的硬性结构校验包括：问题非空且不超过 2000 字；金标准非空（否则回退知识点陈述）且不超过 10000 字；题型强制修正为预期类型；必答要点和可接受答案规范化为字符串列表；证据绑定必须能定位到有效 Block，否则整体回退至源 Block 证据。

随后 M04 对每个生成样本执行一次 LLM 五项检查：

| 质检维度 | 实际判断重点 |
|---|---|
| 可回答性 `answerability` | 给定原文材料能否完整回答问题 |
| 答案忠实性 `faithfulness` | 金标准的每个要点是否有原文支持 |
| 唯一性 `uniqueness` | 是否漏掉其他同样合理的答案 |
| 证据充分性 `evidence_sufficiency` | 已绑定证据是否覆盖所有答案要点 |
| 问题相关性 `question_relevance` | 问题是否真正从文档/知识点导出、未偏题 |

`GET /api/quality-check/results` 的汇总口径为：

| 字段 | 实际定义 |
|---|---|
| `total_cases` | 当前生成样本总数（不等于已经质检的样本数） |
| `passed` / `failed` | **已有质检结果**的 case 中，五项全通过 / 任一失败的 case 数 |
| `by_check_type` | 每个维度的通过数、失败数；维度通过率应计算为 `passed / (passed + failed)` |
| `failed_cases` | 失败 case、失败维度、失败原因和 `review_tag` |
| `errors` | 本轮质检执行异常；不计作维度失败 |

全部通过的样本变为 `quality_verified`。仅“唯一性/证据充分性”失败会标记 `needs_review + answer_coverage` 等待人工确认；“答案忠实性/问题相关性”失败会触发最多两次换角度重生成，仍失败则标记 `needs_review + generation_issue`。因此 M04 结果既是质量指标，也是人工待办来源。

### 4.4 冻结和外部来源的质量约束（M05）

冻结文档生成题时，当前仅快照 M04 可发布态样本：`quality_verified`、`governance_passed`、`user_confirmed`、`published`。冻结后的 `eval_case` 为不可变副本，便于复测和审计。

上传评测集有单独的结构门禁：题目/答案完整率 `data_completeness_rate=100%`、有效 QA 比例 `valid_qa_ratio=100%`、重复问题比例 `duplicate_question_ratio=0`。证据可以缺失。公共库在真实数据未导入时，选择后可能物化 0 题，不会伪造样本。

## 5. 前端实际展示字段和概览口径

### 5.1 问答对字段

| 展示字段 | 后端字段 | 当前定义 |
|---|---|---|
| 问题 | `question` | 发送给目标智能体的输入 |
| 金标准 | `gold_answer` | 用于运行评分的参考答案 |
| 必须命中要点 | `must_have_points` | 质量检查和证据绑定使用的答案事实点；当前运行评分尚未逐点计分 |
| 可接受答案 | `acceptable_answers` | 可接受的同义表达；当前运行评分尚未直接使用 |
| 证据 | `evidence` | 必答要点到原文 Block、章节、页码、原文片段和偏移的绑定 |
| 题型 | `question_type` | 如 definition、rule、threshold、process、exception 等 |
| 难度 | `difficulty` | 题目求解复杂度，L1/L2/L3，前端映射简单/中等/难 |
| 范围 | `scope_type` | 架构允许 `single_segment` / `cross_segment`；当前自动生成主链路固定为 `single_segment` |
| 内容优先级 | `content_priority` | P0/P1/P2，表示业务重要性，不能与难度混用 |
| 审核状态 | `review_status` | candidate、needs_review、quality_verified、published、retired 等 |

当前自动生成难度为确定性规则，而不是 LLM 自由判断：P0 题一律 L2；`threshold/definition/rule/prohibition/exception` 为 L2；`metric/date/process/change/formula` 为 L1。自动主链路不产出 L3。前端“难度分布”仍会预留“难”，但当前生成数据中没有 L3 并不代表零难题能力，只代表跨段/跨文档难题尚未实现。

### 5.2 评测集详情的“五维质量评估”

生成库页面的五维雷达图展示的是 M04 五项检查的逐项通过率：

```text
某项通过率 = 该项 passed / (该项 passed + 该项 failed)
```

如果后端尚未返回 M04 检查结果，页面显示“待后端质量检查”，并采用字段完整性兜底展示，不能将其解释成语义质检通过率。

上传库存在 `quality_snapshot` 时，页面用结构质量快照（有效 QA、完整率、重复率、无证据数）映射展示；没有快照时是前端字段检查兜底。因此上传库雷达图与生成库雷达图不是同一算法，汇报时应标注数据来源，不能横向比较百分比。

### 5.3 首页四张概览卡

| 卡片 | 前端实际计算 | 含义 |
|---|---|---|
| 文档解析健康度 | `解析完成文档数 / 文档总数` | 文档接入进度；同时提示解析失败或待处理数 |
| 待处理事项 | 解析失败 + 知识点待复核 + QA 质检失败 + 被标记待修订的上传集 + 开放 ErrorBook | 运营待办总数，不是质量扣分 |
| 可用评测集 | 已保存的 composition 数量 | 可组合使用的评测集数；副标题显示合计题数 |
| 最新完成评测 | 最近一条完成运行的 `passed_rate` | 评分通过率；同时显示调用错误题数 |

其中“知识点待复核”取 `needs_review_eiu`，并且页面明确提示待复核知识点不进入出题。“生成样本质检待复核”当前取质量汇总的 `failed`，即已有质检结果中存在任一失败项的样本数。

## 6. 目标智能体评测：当前实际指标（M08）

单题评分逻辑：金标准长度不超过 30 字时使用规范化精确匹配；超过 30 字时使用 BGE 语义相似度，模型不可用则退回精确匹配。`score >= 0.5` 判为通过。调用报错为 `error`，无金标准等无法计分为 `unscored`。

**多轮最小评测口径**：评测运行先选择已有的多轮标准答案评测集，再由 m08 按顺序调用目标智能体。最终轮的实际回复仍先复用上述精确/语义评分做错误初筛；对失败或不确定样本，再结合本次请求实际发送的前置对话判断记忆失败、矛盾、约束违反或普通答案错误。`key_turn`、`turn_type`、`depends_on_turns` 是可选的高级标注，不是最小流程的前置条件。当前结果已经保存 `input_turns`、`turn_trace` 和人工 `context_analysis`；但逐轮 memory/coherence 正式分数仍未纳入汇总指标。

| 汇总字段 | 实际定义 |
|---|---|
| `total` | 本次运行结果总数 |
| `scored` | `score` 非空的样本数 |
| `passed` | 已评分样本中 `score >= 0.5` 的数量 |
| `passed_rate` | `passed / scored`；`scored=0` 时为 `null` |
| `error_count` / `error_rate` | `status=error` 的数量 / `total` |
| `by_difficulty` | 每个难度的 `total`、`passed`；后端暂未返回分组通过率 |
| `by_dimension` | 每个维度的 `total`、`passed`；后端暂未返回分组通过率 |
| `total_latency_ms` | 所有样本上报耗时之和 |
| `total_tokens` / `total_cost` | 所有样本上报 Token / 成本之和；适配器未上报时为 0 |
| `diagnosis_distribution` | 诊断码计数 |

当前默认仍是黑盒诊断：答错只记为 `E2E`（端到端失败，不能推断具体根因）；调用异常记为 `D9`。评测运行可以额外启用中间节点评测并选择 `rewrite`、`intent`、`rag` 节点，指标集合固定。`rewrite` 计算语义相似度和有标注时的约束 Precision/Recall/F1；`intent` 只计算意图分类准确率、Macro-F1、分类明细和混淆矩阵；`rag` 使用 RAGAS Context Precision、Context Recall、Faithfulness、Answer Relevancy。外部智能体通过 HTTP 响应路径提供检索文本和节点输出，不绑定平台内部 Block/EIU；未返回所选节点数据时标记 `data_missing`，不计为 0 分。

## 7. 当前未实现或不能作为正式质量结论的指标

下列内容可以作为后续路线，但当前代码没有形成可稳定汇报的真实指标：

- 文档→知识点的人工标注 Precision、Recall、F1、跨块引用召回率、标注者一致性；
- 知识点去重率、冲突识别率、类型/优先级人工准确率；
- 评测集的语义重复率、代表性、跨文档覆盖率、多跳真实性、对抗题占比和拒答覆盖率；
- QA 泛化变体的答案保持率；
- Agent 的检索 Recall@K/MRR/nDCG、要点召回率、引用准确率仍不作为正式指标；RAG 节点当前以 RAGAS 四项指标为准；
- rewrite / intent / rag 以外的目标智能体中间过程、检索结果和关键节点值的分层错因定位。
- 基于多轮上下文的正式逐轮 memory/coherence 分数与校准后的 Judge 指标。

特别是，四项知识点检查的自动通过率不能替代“EIU 抽取准确率”；五项 QA 质检的通过率也不能替代人工校准后的评测集可信度。两者都需要独立的双人标注/仲裁校准集来验证。

## 8. 后续改进优先级

1. **建设知识点校准集与二次评审**：抽样双人标注、仲裁；报告候选 Precision/Recall、跨块证据召回和一致性。对高风险或 `needs_review` 项批量接入 LLM critic，但不以 LLM 自评替代人工基准。
2. **问答泛化**：同一 `intent_id` 下生成同义改写、不同语序、口语/正式表达；变体共享原知识点覆盖，不重复抬高覆盖率。验收指标为“答案保持率”和“变体一致通过率”。
3. **跨段与跨文档题**：先构造多证据知识点，再生成题。只有任一单证据不足、组合证据才足够回答时，才标记为真多跳；同时新增 `cross_segment/cross_document` 范围和证据跳数。
4. **中间结果评测与错因定位**：要求被测 Agent 返回结构化 `final_answer`、检索 Block、关键事实、计算变量/结果、步骤或节点值；再按检索、事实、推理、计算、最终答案分层对齐并形成错因报告。

## 9. 汇报时可直接使用的结论

当前平台已经把“文档—知识点—QA—运行结果”拆成可追溯链路，并且在知识点候选和 QA 样本两个关键环节设置了质量状态，未验证知识点不会自动出题，未通过 QA 质检的生成题不会进入文档生成题的冻结快照。

现阶段最值得汇报的不是一个单一质量总分，而是：文档 Block 是否全部对账、已验证知识点是否被可发布样本覆盖、五项 QA 质检的逐项通过率，以及被测 Agent 的评分通过率和调用错误率。更严格的抽取正确率、跨文档多跳、泛化鲁棒性和细粒度错因定位，已明确为下一阶段建设目标。
